Structured Output Reliability: Why Valid JSON Is Not Enough

The problem

A workflow can return perfectly valid JSON and still make the wrong decision. Consider a ticket-triage assistant that returns a queue, priority, supporting evidence, and a confidence label. The response may satisfy every type constraint while assigning the ticket to the wrong team, quoting irrelevant evidence, or claiming a policy exception that does not exist. A parser will accept the object; the business process should not. This distinction is easy to lose when teams celebrate a high schema-compliance rate as though it measured task reliability. Structured generation is a valuable interface contract, not a substitute for evaluating meaning.

What constrained decoding actually establishes

Grammar- or schema-constrained decoding restricts which tokens can be produced at each step, reducing the chance of syntactically invalid output. Beurer-Kellner, Fischer, and Vechev examine how the implementation of these constraints interacts with tokenization and task accuracy in their ICML 2024 paper on DOMINO. Their result is a warning against treating all constrained decoders as equivalent: the algorithm used to enforce a grammar matters. The JSONSchemaBench research further separates schema coverage, efficiency, and output quality, using a collection of 10,000 real-world schemas. That benchmark size is reported by its authors, not a measurement from this article. Even a successful constrained decode only establishes compliance with the supported portion of the specified schema; it does not establish that a classification or extracted fact is correct.

Schema support is itself an engineering constraint

Provider documentation matters here. OpenAI's Structured Outputs guide describes supported and unsupported JSON Schema features, requires explicit object properties in strict mode, and documents refusal and incomplete-response cases. A system must therefore distinguish at least three outcomes: an accepted schema with a completed response, a refused or incomplete response, and a schema rejected before generation. Treating the latter two as ordinary model predictions corrupts quality metrics. Schema validation should also be performed at the application boundary, rather than assuming a provider contract covers every downstream transformation, serialization step, or future provider migration.

Build an evaluation contract with independent layers

I recommend five separate checks for each example. First, transport completion: did the call finish without truncation, timeout, or refusal? Second, parse and schema validity: can the application decode the response into the expected versioned contract? Third, semantic correctness: do queue, priority, and other fields match the adjudicated answer? Fourth, evidence support: does each decision have a valid supporting source, and does the cited passage actually justify it? Fifth, workflow safety: was any prohibited action requested or performed? This is a proposed engineering framework, not a claim that these five categories were validated in a new experiment. Keep denominators explicit: semantic accuracy among completed valid responses is different from end-to-end successful outcomes across all requests.

A concrete ticket-triage experiment

Define a schema with ticket_id, queue, priority, evidence_ids, and needs_review. The queue and priority should use bounded enums; evidence_ids should reference immutable identifiers from the input evidence set. Create a labeled collection that includes ordinary tickets, ambiguous requests, missing-policy cases, stale policy excerpts, contradictory instructions, and adversarial text embedded in customer descriptions. Freeze the test set and record the authoritative policy version used for labeling. Run the same cases under a baseline prompt, a strict structured-output configuration, and an alternative schema design. Hold model, sampling settings, and retrieved context constant where the API permits. If changing a schema necessarily changes decoding behavior, record that as part of the intervention instead of claiming the comparison isolates prompting alone.

Score fields and cases, not just documents

For each case, record exact-match queue accuracy, priority accuracy, evidence-reference validity, and whether review escalation was appropriate. Add a case-level success metric that requires all mandatory fields to be correct simultaneously. Report refusal and incomplete rates separately. For evidence checks, validate that an identifier exists before asking a reviewer whether the referenced material supports the conclusion. This prevents a model from receiving credit for persuasive prose attached to nonexistent sources. If classes are imbalanced, include per-class recall or a confusion matrix rather than relying only on aggregate accuracy. Track latency and cost per attempted request as well as per successful request; otherwise retries and failures disappear from operational reporting.

Test invariants that a schema cannot express

A JSON schema can say that priority belongs to an allowed enum, but it usually cannot prove that a priority of critical is warranted by a particular policy clause. Implement deterministic invariants when possible: cited evidence IDs must belong to the supplied context; a deprecated queue must never be selected; an action requiring approval must not be executed before approval exists; and needs_review must be true when mandatory evidence is absent. Such checks belong in application logic and integration tests. They should be paired with human-adjudicated semantic cases, because overly rigid business rules can also reject legitimate exceptions. Record both false accepts and false rejects.

Failure modes and limitations

Constrained decoding may alter model behavior, and support for schema keywords varies by implementation; both are reasons to test the exact deployed configuration. Human labels can disagree on ambiguous tickets, so an adjudication protocol and an explicit uncertain class are important. A language-model judge may help triage evaluations, but it can make correlated mistakes and should not be the sole authority for high-impact decisions. Changing policy documents can make yesterday's correct label wrong today, so each test case needs a policy snapshot. Finally, a small curated test suite can miss production distributions; supplement it with privacy-safe samples of observed failures and periodic review. None of these mitigations guarantees safety or correctness.

Three takeaways

1. Treat syntactic compliance, semantic correctness, and evidence support as different properties. A valid object is only the beginning of evaluation. 2. Measure the full request lifecycle, including schema rejection, refusals, incomplete responses, and retries; otherwise reported accuracy can hide failures. 3. Pair constrained decoding with versioned tests, deterministic business invariants, and human review for ambiguous decisions. The aim is an auditable workflow, not a beautiful JSON demo.
