Agent Reliability Is More Than Task Success

An AI agent can pass a task once and still be unreliable. That distinction matters when the system is allowed to call tools, modify state, follow policies, or interact with a user over multiple turns. A single success rate compresses all of that behavior into one number and hides the failure patterns engineers need to understand.

For agentic systems, reliability should answer a harder question: does the system repeatedly make acceptable decisions while respecting constraints across the entire trajectory?

1. Final success hides trajectory quality

AgentBoard was designed around this problem. Its authors argue that evaluating only final task success reveals little about what happened during a multi-step interaction, so the benchmark adds a progress-rate view and tooling for more fine-grained analysis. That is a useful design principle outside the benchmark itself: log intermediate decisions, not just the final outcome.

Consider an agent asked to change a customer reservation. Two runs may end in the same final state, but one may have attempted an unauthorized action, recovered after an error, or called unnecessary tools. If the evaluation stores only “success,” those behaviors disappear.

2. Repeatability is part of correctness

The τ-bench work makes reliability explicit by evaluating agents over repeated trials and introducing pass^k, which asks whether behavior remains successful across multiple attempts. In the paper’s reported experiments, strong function-calling agents were still inconsistent across repeated runs. The broader lesson is durable: stochastic systems should be evaluated for variance, not only mean performance.

A practical test therefore repeats the same scenario several times with controlled randomness. Track the probability of complete success, partial success, policy violation, tool error, unnecessary action, and escalation. A system that succeeds 85% of the time but violates policy in 5% of runs may be less deployable than a slower system with a lower headline success rate and far fewer unsafe trajectories.

3. Use state-based verification whenever possible

Natural-language judges are useful, but they should not be the only source of truth when an environment has machine-checkable state. τ-bench evaluates the resulting database state against an annotated goal state. SWE-bench similarly uses executable tests to determine whether a generated software patch actually resolves a real issue.

This pattern generalizes well. For a workflow agent, define the state that should be true after the task: which record changed, which fields must remain untouched, which approval must exist, and which side effects are forbidden. Then evaluate the terminal state directly. Language-based grading can still assess explanation quality, but state verification makes the core action measurable.

4. Separate capability failures from policy failures

Agent evaluation should distinguish at least four failure families:

  • Planning: the agent chooses an invalid sequence of actions.
  • Tool use: it selects the wrong tool, malformed arguments, or mishandles an error.
  • Policy adherence: it completes the task but violates a rule or permission boundary.
  • Recovery: it fails to recognize that an action did not work and continues from an invalid state.

This taxonomy makes remediation more targeted. Better prompting may help policy adherence; stronger schemas may reduce malformed calls; environment feedback can improve recovery; and a different planner may be needed for long-horizon failures.

5. Build reliability tests from trajectories

The most useful regression set often comes from real failure traces. For every incident or human correction, preserve a sanitized trajectory: starting state, user request, available tools, policy constraints, calls made, observations returned, final state, and reviewer verdict. Convert recurring failures into deterministic regression cases.

Then add adversarial variants. Remove a required permission. Make a tool return a recoverable error. Give two tools similar names. Put a stale instruction next to a current policy. Ask the user to change their mind mid-conversation. Reliable agents need to handle these cases without silently drifting away from the intended state.

6. Report a reliability profile

Instead of one benchmark number, report a compact profile: task success, repeat-success across runs, policy-compliance rate, forbidden-action rate, average tool calls, recovery success, human-escalation rate, and cost/latency. Add confidence intervals when sample sizes permit. The goal is not to maximize the number of metrics; it is to preserve the dimensions that imply different engineering decisions.

Three takeaways

  1. Evaluate trajectories, not just endings. Intermediate actions reveal failures hidden by final success.
  2. Repeat the same task. Reliability is partly about consistency under stochastic execution.
  3. Verify machine state when you can. Use executable or state-based checks for actions, then reserve language judges for dimensions that genuinely require judgment.
